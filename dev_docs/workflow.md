# Development Workflow

このドキュメントは、短期開発中に設計ドキュメント、SSOT、実装、テストを更新するときの運用を定義する。

本プロジェクトは提出までの期間が短いため、全変更で事前承認を待つ運用にはしない。
ただし、設計変更が後から reject されて出戻りになることを避けるため、重要な変更は issue で事前に可視化する。

## 1. 基本方針

公開 API とクラス関係の SSOT は `dev_docs/diagrams/class_overview_diagram.md` とする。

層間契約の理由・ルール・設計決定は `dev_docs/interface.md` に記載する。

実装者は、自分の担当層の public API や層間契約を変更する必要があると判断した場合、実装前に issue を立てて意図を共有する。

issue は承認待ちのためではなく、チームが変更の存在と理由を早めに把握するためのものとする。

## 2. 推奨フロー

通常は以下の順序で進める。

1. 変更が public API、層間契約、所有権、責務分割に影響するか判断する。
2. 影響がある場合は issue を立て、背景、変更案、影響範囲を書く。
3. 実装者の判断で実装を進める。
4. 実装変更に対応するテストを同じ PR に追加・更新する。
5. `make test` などで検証する。
6. 実装と同じ PR、または直後の同期 PR で SSOT / interface / design を更新する。
7. PR では、関連 issue、実装、テスト、ドキュメント更新の対応関係を説明する。

軽微な private 実装変更、リファクタ、バグ修正は issue 必須ではない。

## 3. 実装中に設計問題が見つかった場合

実装前にすべての設計問題を発見できるとは限らない。

実装中に既存 SSOT と実装すべき構造の間に矛盾が見つかった場合は、通常フローに加えて以下を行う。

- issue には、SSOT と実装方針がずれている理由を書く。
- PR には、一時的に何を正として読むべきかを明示する。
- Header / Source / Test のどれが暫定的な実装契約かを明示する。
- 必要なら `dev_docs/decision_*.md` または `dev_docs/knowledge/*.md` に判断を残す。
- 関連しない広範囲のドキュメント更新は、マージ後にまとめて同期してよい。

`decision_*.md` や `knowledge/*.md` は repo に push されるまで他メンバーから見えにくい。
そのため、実装前の共有には issue を優先する。

このフローは、SSOT 後追いを常態化するためのものではない。
短期開発中に見つかった構造的な問題を、実装速度を落としすぎずに共有するための退避手順である。

## 4. レビュー責務

実装者は、担当層の public API と、その API が満たすべきテストを説明する責務を持つ。

隣接層の担当者は、内部実装をすべて理解する必要はない。
次の5点を確認する　①公開 API、②呼び出し条件、③戻り値、④エラー時の扱い、⑤テストで証明されている挙動

レビュー担当者は、以下を確認する。

- SSOT と Header の public API が一致していること。
- `interface.md` の呼び出し元・責務が実装と矛盾していないこと。
- `design.md` の全体構造が現在の実装方針と矛盾していないこと。
- decision / knowledge に残した判断が、必要な場所から参照できること。

## 5. 同期時の確認項目

SSOT と実装を同期するときは、少なくとも以下を確認する。

- 旧 API 名が残っていないこと。
- optional として記載したクラスが、実装済みか未実装か明確であること。
- facade と内部実装の境界が曖昧になっていないこと。
- `_unsafe_*` API の呼び出し元制限が説明されていること。
- テスト方針が実装済み API の責務と一致していること。
