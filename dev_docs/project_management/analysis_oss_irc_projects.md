## 4. ft_ircの参考にできるか？

### Solanum（サーバー）

**結論: 参考にしにくい**

| 問題 | 説明 |
|------|------|
| 規模が大きすぎる | 40MB、プロダクションレベル |
| S2S通信含む | ft_ircでは禁止 |
| IRCv3対応 | ft_ircはRFC 1459/2812相当で十分 |
| Cで書かれている | ft_ircはC++98 |
| 複雑な最適化 | 学習目的には過剰 |

### InspIRCd（C++製サーバー）

**結論: 参考にしにくい**

InspIRCdはC++で書かれているため、ft_ircの参考になるか検討した。

| 項目 | InspIRCd | ft_irc |
|------|----------|--------|
| サイズ | **54 MiB** | - |
| C++バージョン | **C++17相当**（GCC 7+ / Clang 5+） | **C++98** |
| モジュールシステム | あり（高度） | なし |
| S2S通信 | あり | 禁止 |
| IRCv3 | フル対応 | RFC 1459/2812相当 |

| 問題 | 説明 |
|------|------|
| **C++バージョンが違う** | InspIRCdはC++17、ft_ircはC++98。std::string_view、ラムダ式、auto等が使えない |
| **規模が大きすぎる** | 54MB、17,000コミット |
| **設計思想が違う** | 高度なモジュールシステム前提。ft_ircはシンプルな単体プログラム |
| **S2S通信含む** | ft_ircでは禁止 |

### 課題書スペックとの比較

| 機能 | ft_irc | InspIRCd |
|------|:------:|:--------:|
| NICK/USER/PASS | ✅ | ✅ |
| JOIN/PART | ✅ | ✅ |
| PRIVMSG | ✅ | ✅ |
| KICK/INVITE/TOPIC | ✅ | ✅ |
| MODE +i/+t/+k/+o/+l | ✅ | ✅（+多数のモード） |
| S2S通信 | ❌ 禁止 | ✅ |
| モジュールシステム | ❌ | ✅ |
| TLS/SSL | オプション | ✅ |
| IRCv3拡張 | ❌ | ✅ |

### より良い参考資料

| 資料 | 理由 |
|------|------|
| **bircd（課題書添付）** | 学習用、シンプル、select()使用、C言語だが構造がわかりやすい |
| RFC 1459/2812 | プロトコル仕様の一次資料 |
| 書籍 | ソケットプログラミングの基礎 |

**結論:** C++製のInspIRCd（54MiB、C++17）を参考にすることは断念。課題書に添付のbircdが最も適切な参考資料。

## 5. クライアント vs サーバー 難易度比較

### 課題範囲での比較

| 実装項目 | サーバー（ircserv） | クライアント（irssi相当） |
|----------|:------------------:|:------------------------:|
| poll()/多重化 | ◎ 必須（複数fd） | ○ 必要（stdin + socket） |
| バッファリング | ◎ 複数クライアント分 | ○ 1接続分 |
| 状態管理 | ◎ 複数Client/Channel | △ 自分の状態のみ |
| プロトコル解析 | ◎ 全コマンド処理 | ○ 受信メッセージ解析 |
| UI/TUI実装 | ❌ 不要 | ◎ 必須 |
| ユーザー入力処理 | ❌ 不要 | ◎ 必須 |
| ncursesなど | ❌ 不要 | ◎ 必要 |

### 難易度判定

| 観点 | 難しい方 |
|------|----------|
| 状態管理の複雑さ | サーバー |
| 同時接続管理 | サーバー |
| UI実装 | クライアント |
| 外部ライブラリ依存 | クライアント（ncurses等） |
| 総合 | ほぼ同等、方向性が違う |

## 6. ft_ircがサーバー側実装である理由（推測）

### 学習効果の観点

| 技術要素 | サーバー | クライアント |
|----------|:--------:|:------------:|
| poll()/select() | ◎ 必須 | △ あれば便利 |
| ノンブロッキングI/O | ◎ 必須 | △ |
| バッファリング | ◎ 複雑 | ○ シンプル |
| 状態管理 | ◎ 複数クライアント/チャンネル | △ 自分のみ |
| プロトコル解析 | ◎ 全コマンド処理 | △ 受信のみ |

### 参考書籍との対応

「TCP/IPソケットプログラミング C言語編」の内容:
- 5.5 多重化 → poll()で複数クライアント管理
- 5.3.1 ノンブロッキング → 1クライアントに待たされない
- 6章 バッファリング → TCPストリームからメッセージ切り出し

**書籍の内容 ≒ サーバー実装の核心部分**

### 結論

課題がサーバー側実装なのは:
1. poll()/ノンブロッキング/バッファリングを必須で使わせるため
2. 状態管理（複数クライアント/チャンネル）を学ばせるため
3. プロトコル解析（パーサー実装）を学ばせるため

クライアント側はirssi（オープンソース）があるので再発明不要、という理由もあるが、**技術的な学習効果が主な理由**と推測。
